<objective>
Close finding P1-1 from the review: `waitFor` and `_waitForDialogContent` in `content/dom-engine.js` never call `clearTimeout` on the resolve path. When the selector appears and the observer fires, the Promise resolves — but the pending `setTimeout` keeps running. When it eventually fires, it calls `reject(...)` on an already-resolved Promise, which is silently swallowed. The SW's `unhandledrejection` handler still POSTs those phantom errors to `/api/error-log`, polluting telemetry. On slow machines the leak can accumulate 5-8 orphan timers per patient.

Purpose: eliminate silent-rejection pollution in the error-log pipeline.
Output: updated `content/dom-engine.js` with a `clearTimeout` call on the happy path of both `waitFor` and `_waitForDialogContent`.
</objective>

    observer.observe(...);
    setTimeout(() => { observer.disconnect(); reject(new Error(...)); }, timeoutMs);

Refactor so the timeout handle is captured in a variable and cleared on both resolve paths (the initial synchronous check if the element already exists, AND the observer callback when the element appears). The reject path does not need to `clearTimeout` — it's the timer itself firing.

Concretely:
1. `const timeoutHandle = setTimeout(...)`.
2. In the synchronous already-present branch, call `clearTimeout(timeoutHandle)` before resolving.
3. In the observer's "element appeared" branch, call `clearTimeout(timeoutHandle)` before resolving.

Do NOT change the timeout duration, selector logic, or error message.

Be careful if `waitFor` currently checks for the element synchronously BEFORE creating the timeout (to avoid creating a timer that never fires). If so, keep that optimization — just add `clearTimeout` to the observer branch.
