# v3.0.0 — Clerk dashboard setup walkthrough

> **Owner**: USER (manual, ~30 min). Blocks all of v3.0.1+.
> **Output**: 3 secrets + 1 URL that get pasted into Mac Mini env + `popup.html` config.
> **Reference**: `docs/STRATEGY-saas.md` for the why.

## Step-by-step

### 1. Create the Clerk application

1. Go to https://dashboard.clerk.com/ and sign in (or sign up — free tier covers up to 50K MAU).
2. Click **+ Create application**.
3. Name: `Toca Ficha Dr.` (or `tocafichadr-prod`).
4. Sign-in options: enable **Email + Password**. Optionally enable **Google** for one-click sign-in (clinical staff frequently use Gmail).
5. Click **Create application**.

### 2. Configure for Chrome Extension

Clerk needs to know our extension is a Chrome extension client (not a web app):

1. In the new app, go to **Configure → Domains** (or **API Keys → Show advanced**).
2. Under **Frontend API**, copy the URL — looks like `https://clean-bear-12.clerk.accounts.dev`. **Save as `CLERK_FRONTEND_API`**.
3. Go to **Configure → Sessions → Customize session token**. Add this custom claim so Flask sees the email:
   ```json
   {
     "email": "{{user.primary_email_address}}"
   }
   ```
4. Go to **API Keys** in the sidebar.
5. Copy the **Publishable Key** (`pk_test_...` for development, `pk_live_...` for production). **Save as `CLERK_PUBLISHABLE_KEY`**.
6. Click **Show secret key**, copy it (`sk_test_...` / `sk_live_...`). **Save as `CLERK_SECRET_KEY`**. Treat this like an OpenAI key — it goes into Mac Mini Keychain, never into git.
7. The JWKS URL is derived: `<CLERK_FRONTEND_API>/.well-known/jwks.json`. **Save as `CLERK_JWKS_URL`**. Example: `https://clean-bear-12.clerk.accounts.dev/.well-known/jwks.json`.

### 3. Allow the chrome-extension:// origin

This is the tricky part — Clerk by default rejects `chrome-extension://` redirects. Two options depending on Clerk dashboard UI version:

**Option A (preferred, current Clerk UI)**:
1. Go to **Configure → Paths → Allowed redirect origins**.
2. Add: `chrome-extension://<your-extension-id>` — see "Getting your extension ID" below.

**Option B (older UI / API-only)**:
- Use the Clerk Backend API or `clerkClient.allowlistIdentifiers.create()` to add the chrome-extension origin. Documented at https://clerk.com/docs/reference/chrome-extension/overview.

#### Getting your extension ID

The extension ID is generated by Chrome the first time you load the extension. Two paths:

1. **For local development**: load the unpacked extension at `chrome://extensions` → enable Developer Mode → Load unpacked → select the repo dir. Chrome assigns a random ID (e.g., `nfkjmfgmonkpphmlfgmlmddcfpghkdde`). This changes every time you re-load unpacked.
2. **For Web Store distribution**: Chrome Web Store assigns a **stable** ID once you upload the first time (even unpublished). To get a stable ID *before* Web Store submission, use a **persistent extension key** in `manifest.json`:
   ```json
   "key": "<base64-encoded public key>"
   ```
   Generate via `openssl genrsa 2048 | openssl rsa -pubout -outform DER | openssl base64 -A`. Embed the public key, the private key is yours.

**Recommendation**: for v3.0 development, use the dev extension ID. Update Clerk allowed origins right before v3.0.8 (Web Store submit) once we have the production extension ID.

### 4. (Optional but recommended) Configure email templates

If you have time:

1. **Configure → Email**. Edit the verification email and password reset templates to be in Brazilian Portuguese.
2. Add subject lines and body text — clinical users expect formal Portuguese, not English template strings.
3. Toca Ficha Dr. brand: teal `#0891B2`, font Inter (matches landing).

This improves user trust dramatically (Brazilian doctors are wary of English-language SaaS for clinical data).

### 5. Deliver these values back to the next session

Paste this block into the next chat session (or commit to a private secrets store, **never** to git):

```
CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...           # → Mac Mini Keychain as 'pedbot-clerk-secret-key'
CLERK_FRONTEND_API=https://....clerk.accounts.dev
CLERK_JWKS_URL=https://....clerk.accounts.dev/.well-known/jwks.json
EXTENSION_ID_DEV=<32-char id from chrome://extensions>
```

Once this block exists, v3.0.1 (Flask JWKS verify) can ship same-session. v3.0.2 (popup migration) needs `CLERK_PUBLISHABLE_KEY` baked in.

## Common gotchas

- **Test vs Live keys**: Clerk gives separate keys per environment. Use `pk_test_` / `sk_test_` for dev. Switch to `pk_live_` / `sk_live_` only when ready for production traffic. Both work the same; the test instance has lower rate limits and isolated user pools.
- **JWKS rotation**: Clerk rotates signing keys roughly every ~24 hours. The Flask side must re-fetch JWKS on `kid` mismatch (the SDK handles this — don't write your own cache).
- **`syncHost` is for cross-app SSO**: skip it for v3.0. We're not syncing the extension's auth with a separate web app yet.
- **Clerk Backend API rate limits**: 100 req/sec on free tier. We're nowhere near this for normal usage, but `/api/transcribe` calls that look up user metadata could spike. Cache `g.user_id`-to-User-row lookups in-process.

## Open question to answer during setup

- Option (a): keep the 14-day trial. Webhook `user.created` → set `trial_ends_at = now + 14 days` in our `User` row.

**Recommendation**: drop the trial for v3.0. Add it back in v3.1 if conversion metrics demand it. Trials add a code surface that maps poorly onto Clerk's user lifecycle.
